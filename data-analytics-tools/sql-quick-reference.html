SQL Quick Reference

The parts of SQL that come up in analysis work: how a query is actually evaluated, the join and aggregation patterns worth knowing by heart, window functions, and the places where dialects quietly disagree.

Sections

Query skeleton & evaluation order

SQL is written in one order and evaluated in another. Most confusing errors — “column does not exist”, an alias that works in one clause but not another — come from that mismatch.

Written order

SELECT   col, agg(col)
FROM     table
JOIN     other ON ...
WHERE    row_filter
GROUP BY col
HAVING   group_filter
ORDER BY col
LIMIT    n;

Logical evaluation order

1. FROM / JOIN   build the row source
2. WHERE         drop rows (no aggregates yet)
3. GROUP BY      collapse rows into groups
4. HAVING        drop groups (aggregates OK)
5. SELECT        compute output columns
                 window functions run here
6. DISTINCT      de-duplicate
7. ORDER BY      sort (SELECT aliases OK)
8. LIMIT/OFFSET  slice
Consequences. WHERE sees neither aggregates nor SELECT aliases; HAVING sees aggregates; ORDER BY sees aliases; only ORDER BY and LIMIT see a window function’s result.

Filtering a window result needs a wrapper

-- Wrong: at WHERE time the window function has not run yet.
SELECT name, ROW_NUMBER() OVER (ORDER BY score DESC) AS rn
FROM   players
WHERE  rn <= 3;                      -- error: "rn" does not exist

-- Right: compute it in a CTE, filter outside.
WITH ranked AS (
  SELECT name, ROW_NUMBER() OVER (ORDER BY score DESC) AS rn
  FROM   players
)
SELECT name FROM ranked WHERE rn <= 3;

Selecting & shaping rows

Columns, aliases, DISTINCT

SELECT DISTINCT
       u.id                      AS user_id,
       u.first_name || ' ' || u.last_name AS full_name,
       u.score * 1.0 / 100       AS pct
FROM   users AS u;
Always write AS for output columns. A missing comma turns a, b into a AS b and the query still runs.

Sorting

ORDER BY score DESC, name ASC

-- NULL placement (Postgres, Oracle, SQLite 3.30+)
ORDER BY score DESC NULLS LAST

-- Portable equivalent
ORDER BY (score IS NULL), score DESC

-- Sorting by an alias is legal: ORDER BY runs last
SELECT price * qty AS total FROM sales ORDER BY total DESC;

Limiting & paging

-- Postgres, MySQL, SQLite, BigQuery, Snowflake
SELECT * FROM t ORDER BY id LIMIT 20 OFFSET 40;

-- SQL Server / ANSI
SELECT * FROM t ORDER BY id
OFFSET 40 ROWS FETCH NEXT 20 ROWS ONLY;

SELECT TOP 20 * FROM t ORDER BY id;     -- SQL Server
Pair LIMIT with a deterministic ORDER BY. Otherwise you get whichever rows the engine produced first, and that can change between runs. Break ties on a unique column.

CASE — conditional columns

SELECT amount,
       CASE
         WHEN amount >= 1000 THEN 'large'
         WHEN amount >= 100  THEN 'medium'
         ELSE 'small'
       END AS bucket
FROM orders;
Arms are tested top to bottom, so order them most specific first. With no ELSE, unmatched rows get NULL.

Filtering

Predicates

WHERE status = 'active'
  AND price BETWEEN 10 AND 20          -- inclusive at both ends
  AND country IN ('US', 'CA', 'MX')
  AND created_at >= DATE '2026-01-01'
  AND deleted_at IS NULL
  AND score <> 0;                      -- ANSI not-equal (!= also works)

Pattern matching

WHERE email LIKE '%@example.com'    -- % = any run, _ = one character
WHERE name  ILIKE 'ana%'           -- Postgres: case-insensitive
WHERE name  LIKE '100!%' ESCAPE '!'  -- match a literal percent sign
WHERE name  ~ '^A[nl]'             -- Postgres regex
WHERE REGEXP_CONTAINS(name, r'^A') -- BigQuery
A leading % forces a scan — a B-tree index cannot help when the prefix is unknown.

Boolean precedence

-- AND binds tighter than OR, so this is not what it looks like:
WHERE country = 'US' OR country = 'CA' AND active
-- parsed as: country = 'US' OR (country = 'CA' AND active)

-- Say what you mean:
WHERE (country = 'US' OR country = 'CA') AND active

NULL & three-valued logic

NULL means “unknown”, not “empty”. Comparisons against it yield UNKNOWN, and WHERE keeps only rows that are TRUE — so UNKNOWN rows silently disappear.

Testing for NULL

WHERE col IS NULL         -- correct
WHERE col IS NOT NULL

WHERE col = NULL          -- never true, returns nothing
WHERE col <> 'x'          -- drops rows where col IS NULL

-- Keep the NULLs explicitly:
WHERE col <> 'x' OR col IS NULL
WHERE col IS DISTINCT FROM 'x'   -- Postgres: NULL-safe
WHERE NOT (col <=> 'x')          -- MySQL: NULL-safe equality

Substituting a default

COALESCE(a, b, c)        -- first non-NULL argument (ANSI)
NULLIF(a, b)             -- NULL when a = b, else a

IFNULL(a, 0)             -- MySQL, SQLite, BigQuery
ISNULL(a, 0)             -- SQL Server
NVL(a, 0)                -- Oracle

-- Guard a division:
SELECT total / NULLIF(count, 0) AS avg_value FROM t;
NULLIF turns a zero denominator into NULL, so the division returns NULL instead of raising a divide-by-zero error.

NULL in aggregates & keys

COUNT(*)        counts rows, NULLs included
COUNT(col)      skips NULLs in col
SUM, AVG, MIN   skip NULLs  (AVG divides by the non-NULL count)
SUM of no rows  returns NULL, not 0  -> COALESCE(SUM(x), 0)

GROUP BY        groups all NULLs together as one group
ORDER BY        NULLs sort last in Postgres/Oracle DESC-first rules,
                first in MySQL/SQLite -- state NULLS FIRST/LAST
UNIQUE          permits multiple NULLs in most engines

NOT IN with a NULL is a trap

-- If the subquery returns even one NULL, this returns no rows at all:
SELECT * FROM users
WHERE id NOT IN (SELECT user_id FROM orders);   -- user_id nullable!

-- Because: id NOT IN (1, NULL) is UNKNOWN, never TRUE.

-- Safe alternatives:
WHERE id NOT IN (SELECT user_id FROM orders WHERE user_id IS NOT NULL)

SELECT * FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
NOT EXISTS is the habit worth forming — it is NULL-safe and usually plans at least as well.

Joins

The join types

JoinKeeps
INNER JOINOnly rows matching on both sides
LEFT JOINAll left rows; right columns NULL when unmatched
RIGHT JOINMirror of left (rare — reorder and use LEFT)
FULL OUTER JOINAll rows from both sides
CROSS JOINCartesian product, every pair
Plain JOIN means INNER JOIN. MySQL and SQLite have no FULL OUTER JOIN before recent versions — emulate it with LEFT ... UNION ALL ... of the unmatched right rows.

Basic syntax

SELECT o.id, u.email, p.name
FROM       orders   AS o
JOIN       users    AS u ON u.id = o.user_id
LEFT JOIN  products AS p ON p.id = o.product_id
WHERE      o.created_at >= DATE '2026-01-01';

-- USING when the column names match on both sides:
FROM orders JOIN users USING (user_id)

WHERE on the outer table cancels the LEFT JOIN

-- This quietly becomes an INNER JOIN: unmatched rows have
-- o.status = NULL, which fails the WHERE test.
SELECT u.id, o.id
FROM   users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE  o.status = 'paid';

-- Put the condition in the ON clause to keep unmatched users:
LEFT JOIN orders o ON o.user_id = u.id AND o.status = 'paid';
Rule of thumb: conditions on the optional side of an outer join belong in ON; conditions on the preserved side belong in WHERE.

Anti-join — rows with no match

-- Users who have never ordered.
SELECT u.*
FROM   users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE  o.user_id IS NULL;

-- Same thing, usually clearer and NULL-safe:
SELECT u.* FROM users u
WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.user_id = u.id
);

Semi-join — matched, but no duplication

-- EXISTS stops at the first match, so one row per user.
SELECT u.* FROM users u
WHERE EXISTS (
  SELECT 1 FROM orders o
  WHERE o.user_id = u.id AND o.total > 100
);

-- A plain JOIN would repeat the user once per qualifying order.

Self-join

-- Each employee next to their manager.
SELECT e.name AS employee, m.name AS manager
FROM   employees e
LEFT JOIN employees m ON m.id = e.manager_id;
Aliases are mandatory here — they are the only way to tell the two copies of the table apart.

Fan-out: the silent double-count

-- If a user has 3 orders, the user's row repeats 3 times and
-- any aggregate over user columns is inflated.
SELECT u.id, SUM(u.credit)       -- WRONG: credit counted 3x
FROM   users u JOIN orders o ON o.user_id = u.id
GROUP BY u.id;

-- Aggregate first, then join one row to one row:
SELECT u.id, u.credit, o.order_count
FROM   users u
LEFT JOIN (
  SELECT user_id, COUNT(*) AS order_count
  FROM   orders GROUP BY user_id
) o ON o.user_id = u.id;
Whenever a join makes a total grow unexpectedly, check the grain: a join is only safe for aggregation when the right side is unique on the join key.

Grouping & aggregation

Aggregate functions

COUNT(*)              rows in the group
COUNT(col)            non-NULL values
COUNT(DISTINCT col)   distinct non-NULL values
SUM(col)  AVG(col)  MIN(col)  MAX(col)
STDDEV(col)  VARIANCE(col)

-- String rollup (dialect-specific):
STRING_AGG(name, ', ' ORDER BY name)  -- Postgres, SQL Server, BigQuery
GROUP_CONCAT(name)                    -- MySQL, SQLite
LISTAGG(name, ', ')                   -- Oracle, Snowflake

GROUP BY and HAVING

SELECT   country, COUNT(*) AS n, AVG(total) AS avg_total
FROM     orders
WHERE    created_at >= DATE '2026-01-01'   -- filter rows first
GROUP BY country
HAVING   COUNT(*) >= 10                    -- then filter groups
ORDER BY n DESC;
Every non-aggregated SELECT column must appear in GROUP BY. Postgres relaxes this when you group by a primary key; MySQL relaxes it further unless ONLY_FULL_GROUP_BY is on — do not rely on either.

Conditional aggregation

-- Several measures in one pass over the table.
SELECT country,
       COUNT(*)                                        AS orders,
       COUNT(*) FILTER (WHERE status = 'paid')         AS paid,
       SUM(CASE WHEN status = 'paid' THEN total END)   AS paid_total,
       AVG(CASE WHEN status = 'paid' THEN total END)   AS paid_avg
FROM   orders
GROUP BY country;
FILTER (WHERE ...) is ANSI and supported by Postgres and SQLite. The CASE form works everywhere: the implicit ELSE NULL is what keeps non-matching rows out of the aggregate.

Pivoting with CASE

SELECT product,
       SUM(CASE WHEN quarter = 'Q1' THEN revenue ELSE 0 END) AS q1,
       SUM(CASE WHEN quarter = 'Q2' THEN revenue ELSE 0 END) AS q2,
       SUM(CASE WHEN quarter = 'Q3' THEN revenue ELSE 0 END) AS q3,
       SUM(CASE WHEN quarter = 'Q4' THEN revenue ELSE 0 END) AS q4
FROM   sales
GROUP BY product;

Subtotals: ROLLUP, CUBE, GROUPING SETS

-- Country totals, plus a grand total row.
SELECT country, city, SUM(total)
FROM   orders
GROUP BY ROLLUP (country, city);

-- Every combination of the two dimensions.
GROUP BY CUBE (country, city)

-- Exactly the combinations you name.
GROUP BY GROUPING SETS ((country), (city), ())

-- Tell a subtotal NULL apart from a real one:
SELECT GROUPING(city) AS is_subtotal, ...

Percentiles

SELECT
  PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY total) AS median,
  PERCENTILE_CONT(0.9) WITHIN GROUP (ORDER BY total) AS p90
FROM orders;

-- MySQL / BigQuery use APPROX_QUANTILES or window forms instead.
PERCENTILE_CONT interpolates between values; PERCENTILE_DISC returns an actual value from the data.

Window functions

A window function computes across a set of related rows but, unlike GROUP BY, keeps every row. This is the single highest-leverage part of SQL for analysis.

Anatomy

function() OVER (
  PARTITION BY col      -- restart the calculation per group (optional)
  ORDER BY     col      -- order within the partition (required for ranking)
  ROWS BETWEEN ...      -- frame: which rows feed the calculation
)

-- Reuse one definition across several columns:
SELECT name,
       SUM(total)   OVER w AS running_total,
       ROW_NUMBER() OVER w AS n
FROM   orders
WINDOW w AS (PARTITION BY user_id ORDER BY created_at);

Ranking

ROW_NUMBER()  1,2,3,4   always distinct, ties broken arbitrarily
RANK()        1,2,2,4   ties share a rank, then it skips
DENSE_RANK()  1,2,2,3   ties share a rank, no gap
NTILE(4)      splits the partition into 4 buckets
PERCENT_RANK()  CUME_DIST()

SELECT name, department, salary,
       RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS r
FROM employees;

Top N per group

-- The three highest-paid people in each department.
WITH ranked AS (
  SELECT name, department, salary,
         ROW_NUMBER() OVER (PARTITION BY department
                            ORDER BY salary DESC, name) AS rn
  FROM   employees
)
SELECT name, department, salary
FROM   ranked
WHERE  rn <= 3;
Use ROW_NUMBER for “exactly three” and RANK for “three, plus anyone tied for third”. Add a tiebreaker to ORDER BY so the result is reproducible.

Comparing to neighbouring rows

SELECT day, revenue,
       LAG(revenue)  OVER (ORDER BY day) AS prev_day,
       LEAD(revenue) OVER (ORDER BY day) AS next_day,
       revenue - LAG(revenue) OVER (ORDER BY day) AS change,
       FIRST_VALUE(revenue) OVER (ORDER BY day) AS first_day
FROM   daily_revenue;

LAG(col, 2, 0)   -- two rows back, 0 when there is none

Running totals & moving averages

SELECT day, revenue,
       -- running total from the start of the partition
       SUM(revenue) OVER (
         ORDER BY day
         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_total,

       -- trailing 7-row average
       AVG(revenue) OVER (
         ORDER BY day
         ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
       ) AS avg_7
FROM daily_revenue;

Frames: ROWS vs RANGE

ROWS BETWEEN 6 PRECEDING AND CURRENT ROW     -- counts rows
RANGE BETWEEN INTERVAL '6 days' PRECEDING
          AND CURRENT ROW                    -- counts values

-- Default frame when ORDER BY is present but no frame is given:
RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
That default is RANGE, so tied ORDER BY values are all folded into the current row — a “running total” jumps in steps when a day has several rows. Write ROWS explicitly when you mean row counts.

Share of total without a self-join

SELECT department, name, salary,
       salary * 100.0
         / SUM(salary) OVER (PARTITION BY department) AS pct_of_dept,
       salary - AVG(salary) OVER (PARTITION BY department) AS vs_dept_avg
FROM   employees;
Omitting ORDER BY makes the frame the whole partition — which is exactly what a denominator wants.

Deduplicating

-- Keep the most recent row per key.
WITH numbered AS (
  SELECT *,
         ROW_NUMBER() OVER (PARTITION BY email
                            ORDER BY updated_at DESC) AS rn
  FROM   users
)
SELECT * FROM numbered WHERE rn = 1;

CTEs & subqueries

WITH — naming the steps

WITH recent_orders AS (
  SELECT * FROM orders WHERE created_at >= DATE '2026-01-01'
),
per_user AS (
  SELECT user_id, COUNT(*) AS n, SUM(total) AS spend
  FROM   recent_orders
  GROUP BY user_id
)
SELECT u.email, p.n, p.spend
FROM   per_user p
JOIN   users u ON u.id = p.user_id
WHERE  p.spend > 500;
A later CTE can reference an earlier one, which is what makes a long transformation readable top to bottom.

Subquery positions

-- Scalar: must return one row, one column
SELECT name, (SELECT AVG(salary) FROM employees) AS company_avg
FROM employees;

-- Derived table: in FROM, alias required
SELECT d.department, d.avg_salary
FROM  (SELECT department, AVG(salary) AS avg_salary
       FROM employees GROUP BY department) AS d;

-- Correlated: re-evaluated per outer row
SELECT e.name
FROM   employees e
WHERE  e.salary > (SELECT AVG(salary) FROM employees
                   WHERE department = e.department);

Recursive CTE

-- Walk an org chart down from the top.
WITH RECURSIVE chain AS (
  SELECT id, name, manager_id, 1 AS depth       -- anchor
  FROM   employees WHERE manager_id IS NULL
  UNION ALL
  SELECT e.id, e.name, e.manager_id, c.depth + 1 -- recursive step
  FROM   employees e
  JOIN   chain c ON e.manager_id = c.id
  WHERE  c.depth < 10                            -- guard
)
SELECT * FROM chain ORDER BY depth;
Always bound the recursion. A cycle in the data with no depth guard runs until the server kills the query. SQL Server omits the RECURSIVE keyword.

Generating a date series

-- Postgres: a row per day, so reports show zero-activity days.
SELECT d::date AS day
FROM generate_series(DATE '2026-01-01', DATE '2026-01-31',
                     INTERVAL '1 day') AS d;

-- Portable: recursive CTE
WITH RECURSIVE days(day) AS (
  SELECT DATE '2026-01-01'
  UNION ALL
  SELECT day + 1 FROM days WHERE day < DATE '2026-01-31'
)
SELECT * FROM days;
LEFT JOIN your data onto the series to turn missing days into explicit zeros rather than absent rows.

CTE performance

-- Postgres < 12 always materialised a CTE (an optimisation fence).
-- Postgres 12+ inlines single-use CTEs; force it either way:
WITH x AS MATERIALIZED     (...)
WITH x AS NOT MATERIALIZED (...)
A CTE referenced several times may be computed several times in some engines. If it is expensive, write it to a temporary table instead.

Set operations

UNION, INTERSECT, EXCEPT

SELECT id FROM a UNION     SELECT id FROM b;  -- both, de-duplicated
SELECT id FROM a UNION ALL SELECT id FROM b;  -- both, duplicates kept
SELECT id FROM a INTERSECT SELECT id FROM b;  -- in both
SELECT id FROM a EXCEPT    SELECT id FROM b;  -- in a, not in b
                                              -- MINUS in Oracle
Column count and types must line up; names come from the first branch. ORDER BY applies to the whole result and goes last.

Prefer UNION ALL

-- UNION sorts or hashes everything to remove duplicates.
-- When the branches cannot overlap, that work is wasted:
SELECT id, 'web'    AS source FROM web_orders
UNION ALL
SELECT id, 'mobile' AS source FROM mobile_orders;

Strings, dates & casting

Strings

LENGTH(s)            CHAR_LENGTH(s)
UPPER(s)  LOWER(s)   TRIM(s)  LTRIM(s)  RTRIM(s)
SUBSTRING(s FROM 2 FOR 5)     SUBSTR(s, 2, 5)
REPLACE(s, 'a', 'b')          POSITION('x' IN s)
LEFT(s, 3)  RIGHT(s, 3)       LPAD(s, 5, '0')
SPLIT_PART(s, ',', 2)         -- Postgres

'a' || 'b'           -- ANSI, Postgres, SQLite, Oracle
CONCAT('a', 'b')     -- everywhere
'a' + 'b'            -- SQL Server
Escape a literal quote by doubling it: 'O''Brien'.

Dates & times

CURRENT_DATE   CURRENT_TIMESTAMP        -- ANSI
NOW()          -- Postgres, MySQL
GETDATE()      -- SQL Server

DATE_TRUNC('month', ts)                -- Postgres, Snowflake, BigQuery
EXTRACT(YEAR FROM ts)  EXTRACT(DOW FROM ts)
ts + INTERVAL '7 days'                 -- Postgres
DATEADD(day, 7, ts)                    -- SQL Server
DATE_ADD(ts, INTERVAL 7 DAY)           -- MySQL
AGE(a, b)  /  DATEDIFF(day, a, b)      -- differences

Half-open date ranges

-- BETWEEN on a timestamp silently drops most of the last day,
-- because '2026-01-31' means midnight at its start.
WHERE ts BETWEEN '2026-01-01' AND '2026-01-31'   -- misses 00:00:01+

-- Use a half-open interval instead:
WHERE ts >= DATE '2026-01-01'
  AND ts <  DATE '2026-02-01'
Half-open ranges also tile cleanly: consecutive months never overlap and never leave a gap.

Casting

CAST(x AS INTEGER)       -- ANSI, portable
x::numeric               -- Postgres shorthand
TRY_CAST(x AS INT)       -- SQL Server: NULL instead of an error
SAFE_CAST(x AS INT64)    -- BigQuery

-- Integer division truncates in most engines:
SELECT 7 / 2;            -- 3
SELECT 7 * 1.0 / 2;      -- 3.5
SELECT CAST(7 AS numeric) / 2;
Use NUMERIC/DECIMAL for money. Binary FLOAT cannot represent 0.1 exactly and the error accumulates across a SUM.

Inserting, updating, deleting

INSERT

INSERT INTO users (email, name) VALUES
  ('a@example.com', 'Ada'),
  ('b@example.com', 'Blaise');

-- From a query
INSERT INTO archive (id, total)
SELECT id, total FROM orders WHERE created_at < DATE '2025-01-01';

-- Get the generated keys back
INSERT INTO users (email) VALUES ('c@example.com') RETURNING id;
Name the columns explicitly. Positional inserts break the moment someone adds a column.

UPDATE & DELETE

UPDATE users SET name = 'Ada L.', updated_at = NOW()
WHERE id = 42;

-- Update from another table (Postgres)
UPDATE orders o
SET    country = u.country
FROM   users u
WHERE  u.id = o.user_id;

DELETE FROM sessions WHERE expires_at < NOW();
TRUNCATE TABLE staging;     -- all rows, no WHERE, minimal logging
Run the WHERE as a SELECT first. Check the row count, then wrap the write in a transaction so a surprise can be rolled back.

Upsert

-- Postgres, SQLite
INSERT INTO users (email, name) VALUES ('a@example.com', 'Ada')
ON CONFLICT (email) DO UPDATE SET name = EXCLUDED.name;

ON CONFLICT (email) DO NOTHING;

-- MySQL
INSERT INTO users (email, name) VALUES ('a@example.com', 'Ada')
ON DUPLICATE KEY UPDATE name = VALUES(name);

-- ANSI / SQL Server / Snowflake
MERGE INTO users AS t USING staged AS s ON t.email = s.email
WHEN MATCHED     THEN UPDATE SET name = s.name
WHEN NOT MATCHED THEN INSERT (email, name) VALUES (s.email, s.name);

Transactions

BEGIN;
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;        -- or ROLLBACK;

SAVEPOINT sp1;  ROLLBACK TO sp1;
DDL is transactional in Postgres, so a migration can be rolled back. MySQL and Oracle commit implicitly on DDL — there is nothing to undo.

Tables, constraints & views

CREATE TABLE

CREATE TABLE orders (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id     BIGINT      NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  total       NUMERIC(12,2) NOT NULL CHECK (total >= 0),
  status      TEXT        NOT NULL DEFAULT 'pending',
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  UNIQUE (user_id, created_at)
);
Auto-increment differs: SERIAL/IDENTITY (Postgres), AUTO_INCREMENT (MySQL), IDENTITY(1,1) (SQL Server), INTEGER PRIMARY KEY (SQLite).

Constraints

PRIMARY KEY   unique + NOT NULL, one per table
FOREIGN KEY   must match a row in the referenced table
UNIQUE        no duplicates (NULLs usually exempt)
NOT NULL      value required
CHECK         arbitrary row-level predicate
DEFAULT       value used when the column is omitted

ON DELETE CASCADE | SET NULL | RESTRICT | NO ACTION

ALTER & DROP

ALTER TABLE orders ADD COLUMN notes TEXT;
ALTER TABLE orders ALTER COLUMN status SET DEFAULT 'new';
ALTER TABLE orders DROP COLUMN notes;
ALTER TABLE orders RENAME TO customer_orders;

DROP TABLE IF EXISTS staging;
CREATE TABLE tmp AS SELECT * FROM orders WHERE 1 = 0;  -- structure only

Views

CREATE VIEW active_users AS
SELECT * FROM users WHERE deleted_at IS NULL;

CREATE OR REPLACE VIEW ...
DROP VIEW IF EXISTS active_users;

-- Materialised: stored, must be refreshed
CREATE MATERIALIZED VIEW daily_totals AS
SELECT DATE_TRUNC('day', created_at) AS day, SUM(total) FROM orders
GROUP BY 1;
REFRESH MATERIALIZED VIEW daily_totals;
A plain view is a stored query with no data of its own — it costs what the underlying query costs, every time.

Performance

Read the plan first

EXPLAIN ANALYZE SELECT ...;     -- Postgres: estimates + real timings
EXPLAIN SELECT ...;             -- MySQL, SQLite
SET SHOWPLAN_ALL ON;            -- SQL Server
Look for a sequential scan on a large table, a row-count estimate far from actual, and the step where time is actually spent. Optimise that step, not the query you assume is slow.

Indexes

CREATE INDEX idx_orders_user ON orders (user_id);
CREATE INDEX idx_orders_user_date ON orders (user_id, created_at);
CREATE UNIQUE INDEX idx_users_email ON users (email);
CREATE INDEX idx_active ON orders (user_id) WHERE status = 'active';
A composite index serves any prefix of its columns: (user_id, created_at) helps a lookup on user_id alone, but not on created_at alone. Indexes cost write speed and storage, so add them for real queries, not on principle.

Keep predicates sargable

-- Wrapping the column in a function hides the index:
WHERE YEAR(created_at) = 2026
WHERE UPPER(email) = 'A@EXAMPLE.COM'

-- Rewrite so the bare column faces the operator:
WHERE created_at >= DATE '2026-01-01'
  AND created_at <  DATE '2027-01-01'
WHERE email = LOWER('A@example.com')   -- with a lowercase column

-- Or index the expression itself:
CREATE INDEX idx_users_email_lower ON users (LOWER(email));

Common wins

  • Select the columns you need; SELECT * blocks index-only scans.
  • Filter before you join, so fewer rows reach the join.
  • EXISTS over IN for large subqueries.
  • UNION ALL over UNION unless you truly need the dedup.
  • Avoid DISTINCT used to paper over a fan-out — fix the join grain.
  • Keep statistics fresh (ANALYZE); bad estimates give bad plans.
  • Batch large writes; one huge transaction blocks and bloats.
